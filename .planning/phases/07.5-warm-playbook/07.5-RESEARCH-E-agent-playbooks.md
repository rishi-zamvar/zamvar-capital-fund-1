# 07.5 RESEARCH E — How production teams build PLAYBOOKS for LLM agents (structured + narrative node design)

**Scope:** Design Q1 (content + schema of a playbook node) informed by how the best production
agent teams structure the knowledge/playbook units their models reason from. Answers: what a
DoorDash / Sierra / Decagon / Fin / memory-system "node" contains, the split between **structured
filter-fields** (routing/retrieval) and the **natural-language body** (reasoning), how they author /
version / retrieve / evaluate them, and — the payload — a recommended structure for **our
catalyst-outcome playbook node** that maps directly onto the existing `kb.py` scaffold (see RESEARCH C).

Everything external is cited inline. Frugality: WebSearch/WebFetch only.

---

## 0. Executive summary — the one pattern everyone converges on

Every serious production agent team has independently landed on the **same hybrid node shape**:

> **A small set of STRUCTURED fields the retrieval/routing layer reads deterministically, wrapped
> around a RICH NATURAL-LANGUAGE body the model actually reasons from — and the body is grounded to
> cited sources, single-topic, written at a deliberate "altitude" (heuristics, not brittle rules),
> and versioned/temporally-scoped so stale or conflicting entries can be invalidated without deletion.**

Concretely, the shared design has five load-bearing properties:

1. **Structured envelope, narrative core.** Structured fields = *when/whether this node applies* (type,
   scope, applicability tags, validity window, confidence, source refs). Narrative body = *what
   happened and why, and what to do about it* — the thing embedded and put in-context. DoorDash,
   Sierra, Decagon, Fin, Letta all draw this line the same way.
2. **Single-topic granularity.** One node = one situation/procedure/fact. "A few paragraphs or even a
   few sentences." Big documents get chunked to this size before they become retrievable nodes.
3. **Right-altitude narrative.** Not brittle hardcoded rules (fragile, high-maintenance) and not vague
   platitudes — "specific enough to guide behavior, flexible enough to give the model strong
   heuristics" (Anthropic). This is *why* narrative-in-context beat decision trees for these teams.
4. **Grounded + cited.** The body states an explicit outcome/resolution and is traceable to a source;
   deterministic/critical facts are pulled from structured systems, not generated by the LLM.
5. **Versioned + temporally scoped.** Immutable release snapshots (Sierra) and/or bi-temporal
   valid/invalid windows per fact (Zep/Graphiti) so conflicting entries are *invalidated, not
   discarded*, preserving history and provenance — directly relevant to our 07.6 bitemporal cutoff.

The rest of this doc is the evidence, then §4 is the concrete node schema for our KB.

## 1. DoorDash — the deepest published example

DoorDash has published a multi-part engineering series ("Ask DoorDash", Parts 1–4) plus a Dasher-support
RAG writeup. Their direct blog blocks scraping (403), so citations below draw on the DoorDash blog URLs
plus the ZenML LLMOps-database mirrors and InfoQ's writeup of the same material.

### 1.1 What a DoorDash "playbook / knowledge unit" is

DoorDash runs **two distinct knowledge surfaces**, and it matters which one maps to our "playbook":

- **Dasher-support RAG knowledge**: existing help-center articles + **historical resolved cases**,
  retrieved by semantic similarity. The retrieval unit is an article/case; the multi-turn conversation
  is first **condensed into a single core-issue query**, that query is matched against articles + past
  cases, and the hit is dropped into a **template-based prompt** for generation
  ([DoorDash, "Path to high-quality LLM-based Dasher support automation"](https://careersatdoordash.com/blog/large-language-modules-based-dasher-support-automation/);
  [ZenML mirror](https://www.zenml.io/llmops-database/building-a-high-quality-rag-based-support-system-with-llm-guardrails-and-quality-monitoring)).
  Note: historical *cases with their outcomes* as retrievable units is exactly our "past catalyst →
  outcome" analog pattern.
- **Ask DoorDash agent behavior**: agents are modeled as a **computational graph / finite-state
  machine** — "executable nodes with defined transitions… states representing task steps and
  transition rules governing movement between states" (LangGraph)
  ([DoorDash Part 4](https://careersatdoordash.com/blog/building-ask-doordash-part-four-a-platform-for-building_and_evolving_agents/);
  [ZenML: collaborative multi-agent ecosystem](https://www.zenml.io/llmops-database/building-a-collaborative-multi-agent-ai-ecosystem-for-enterprise-knowledge-access)).
  Behavior "playbook" here = the graph of steps + tool-calls, not a prose doc.

### 1.2 The grounding decision — "doesn't rely on the LLM alone"

The single most transferable DoorDash lesson: **knowledge is held in structured memory and structured
systems, NOT embedded in the prompt, and critical operations are deterministic, not LLM-generated.**
InfoQ's writeup of Ask DoorDash is explicit:

- Three-tier memory: **long-term** (offline-generated from historical behavior — e.g. preferences),
  **session** (conversational context), **agentic** (explicit facts the user provided). Memories are
  "retrieved through semantic vector search, ranked, and incorporated into prompts, **separating memory
  management from model inference**."
- **Deterministic grounding**: "deterministic actions that update versioned artifacts without invoking
  the language model, and confirmation workflows for recommendations and generated carts."
  ([InfoQ, "How DoorDash Built an AI Shopping Assistant That Doesn't Rely on the LLM Alone"](https://www.infoq.com/news/2026/07/doordash-ai-ask-assistant/)).

Tooling is exposed through a **Model Context Protocol layer + Agent Gateway / tool registry**: 200+
registered MCP servers, millions of weekly tool calls, each tool "a focused operation with the inputs
and outputs the model needs" — auditable, authorized access to knowledge/ops rather than free-form
retrieval ([DoorDash: centralized gateway](https://careersatdoordash.com/blog/how-doordash-built-a-centralized-gateway-for-ai-agent-tool-access/);
[ZenML mirror](https://www.zenml.io/llmops-database/centralized-gateway-for-ai-agent-tool-access)).

### 1.3 Authoring, versioning, retrieval, evaluation

- **Authoring/evolving**: a common platform lets *domain teams* build/evolve agents "without rebuilding
  the systems beneath them," judged by how fast teams can add features and how fast they can evaluate +
  release improvements ([Part 4](https://careersatdoordash.com/blog/building-ask-doordash-part-four-a-platform-for-building_and_evolving_agents/)).
- **Retrieval**: condense-then-match (support) / semantic vector search + rank (Ask). Query refinement
  before retrieval is a recurring step.
- **Evaluation (the flywheel — the headline result)**: a **simulation + eval framework** runs
  predefined Q&A scenarios against agents using **LLM-generated users and recorded tool fixtures** that
  "mirror the production runtime," plus an **LLM-Judge** scoring five metrics — *retrieval correctness,
  response accuracy, grammar/language accuracy, coherence to context, relevance to request* — and a
  two-tier **LLM Guardrail** checking *groundedness, coherence, policy compliance*. Result:
  **hallucinations −90%, severe compliance issues −99%**, and the simulation gains carried into
  production ([DoorDash simulation/eval flywheel](https://careersatdoordash.com/blog/doordash-simulation-evaluation-flywheel-to-develop-llm-chatbots-at-scale/);
  [ZenML mirror](https://www.zenml.io/llmops-database/building-a-high-quality-rag-based-support-system-with-llm-guardrails-and-quality-monitoring)).

### 1.4 Why narrative-in-context beat brittle rules (DoorDash's own framing)

DoorDash's shift from static flows to graph-of-steps + retrieved narrative context is the same lesson
Decagon and Anthropic state directly (§2.2, §2.5): decision trees/hardcoded flows are "linear and
static" and break on real-world variety; retrieved narrative + heuristics generalize. But DoorDash's
guardrail against the failure mode of *pure* narrative is (a) deterministic grounding for anything
critical and (b) the LLM-Judge/guardrail eval loop — narrative for reasoning, structure/code for facts
and safety.

## 2. Other production agent-playbook patterns

### 2.1 Sierra — declarative skills + immutable knowledge snapshots

Sierra separates *procedural knowledge* (how things are done) from *retrieved knowledge* (facts):

- Behavior is **declarative**, not free-prompt: developers "declare the behaviours they want… abstracted
  from the underlying LLMs" via composable **skills** expressing procedural knowledge, combining
  **Goals** ("help the customer return an order") with **Guardrails** ("orders can only be returned
  within 30 days" — deterministic safeguards).
- Knowledge-base docs cover both "customer-facing product specifications" and **internal agent
  protocols** — dispute procedures, card-replacement workflows, retention offers, identity verification
  ([Contrary Research: Sierra breakdown](https://research.contrary.com/company/sierra)).
- **Versioning = immutable release snapshot**: "each agent release is a snapshot that includes not only
  the underlying source code and prompts, but model version dependencies and **an immutable snapshot of
  all of the knowledge available to the agent**." Journeys can be AI-generated from existing operating
  procedures; Sierra auto-flags common themes missing from the KB.
- **Evaluation**: SMEs annotate conversations ("Did the agent make the correct decision? correct
  language/tone?") and **every annotated conversation becomes a regression test** replayed against mock
  APIs ([Sierra: Agent Development Life Cycle](https://sierra.ai/uk/blog/agent-development-life-cycle);
  [Sierra: Agent Studio](https://sierra.ai/product/configure-your-agent)).

**Takeaway for us:** freeze the knowledge that produced a decision alongside the decision (snapshot),
and treat facts/limits as deterministic guardrails distinct from the reasoning narrative.

### 2.2 Decagon — Agent Operating Procedures (AOPs): natural language that compiles to structured logic

Decagon's whole thesis *is* the hybrid node:

- An **AOP** = "natural language instructions that compile into structured logic for AI agents to
  reliably execute workflows" — "the power and flexibility of natural language with the precision and
  rigor of code." Business teams author the natural-language instructions; engineers build/maintain the
  executable logic + integrations underneath.
- Three principles: **Speed to build** (business + eng author in parallel), **Flexibility** (blends
  "conversational instructions with code-based logic"), **Guardrails** (safety-critical **validation
  steps run in code**, not prose).
- Rationale — explicitly against brittle rules: "traditional decision trees are inherently linear and
  static" and fail under real-world unpredictability; a natural-language framework is "fluid and
  scalable"
  ([Decagon: Why we built AOP](https://decagon.ai/resources/why-we-built-aop);
  [Decagon: From SOPs to AOPs](https://decagon.ai/blog/from-sops-to-agent-operating-procedures);
  [Decagon AOP product](https://decagon.ai/product/aop)).

**Takeaway for us:** narrative for reasoning, code/structured fields for anything that must be exact
(the signed move, the outcome enum, the as-of gate) — mirror the AOP split.

### 2.3 Intercom / Fin — bespoke RAG with query-refine → ground → validate, plus "Guidance"

- Fin runs a **6-layer pipeline**: refine query (interpret intent/context) → retrieve with proprietary
  models → **rerank** → generate a **grounded** answer/action → **validate accuracy** → optimize. Query
  refinement and a separate validation pass bracket the generation, same as DoorDash.
- Knowledge lives in a **Knowledge Hub** aggregating many source types (help articles, internal docs,
  **snippets**, synced pages, PDFs, live data via connectors). On top of content, **Fin Guidance** lets
  humans "coach Fin on how it should answer" with custom instructions (policy/tone), and **Fin
  Tasks/Procedures** encode multi-step workflows — i.e. content (facts) + guidance (behavior) +
  procedures (steps) are three distinct layers
  ([Fin: AI Knowledge Base guide](https://fin.ai/learn/ai-knowledge-base);
  [Intercom: Fin AI Agent explained](https://www.intercom.com/help/en/articles/7120684-fin-ai-agent-explained)).
  (Fin was acquired into Salesforce **Agentforce**, June 2026.)

### 2.4 Salesforce Agentforce & OpenAI Agents SDK — behavior as instructions + guardrails + handoffs

- **Agentforce**: grounded on the org's data/knowledge; notably "turns resolved conversations into
  knowledge articles" — the resolved-case-becomes-node loop again
  ([Fin/Salesforce coverage](https://fin.ai/learn/ai-knowledge-base)).
- **OpenAI Agents SDK**: an Agent = **name + instructions (its system prompt) + tools + guardrails +
  handoffs**. Instructions "define behavior, knowledge boundaries, and how it should respond";
  **guardrails run in parallel** to validate I/O and enforce boundaries; **handoffs** route to
  specialized agents (triage → specialist), the specialist seeing prior history
  ([OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/);
  [OpenAI Agents SDK: Guardrails](https://openai.github.io/openai-agents-python/guardrails/)).

### 2.5 Anthropic — "context engineering" and the right altitude for the narrative body

The clearest guidance on *how to write the narrative field* itself:

- **Right altitude**: avoid two failure modes — **too brittle** ("hardcoding complex, brittle logic in
  prompts… creates fragility and increases maintenance") and **too vague** (no "concrete signals," or
  "falsely assume shared context"). Target: "specific enough to guide behavior effectively, yet
  flexible enough to provide the model with strong heuristics."
- **Structure the context** into labeled sections (`<background_information>`, `<instructions>`,
  `## Tool guidance`, `## Output description`) via XML/markdown. Seek "the minimal set of information
  that fully outlines expected behavior" — "minimal does not necessarily mean short."
- **Just-in-time retrieval**: prefer lightweight identifiers (paths/queries/links) loaded on demand
  over pre-loading everything, to protect the "limited attention budget"
  ([Anthropic: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents);
  [Claude Cookbook: context engineering](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)).

### 2.6 Agent-memory systems — Letta / Zep / Mem0 — the node schemas, verbatim

These give the most explicit **field-level** schemas.

- **Letta (MemGPT) memory block** — the cleanest structured-node schema in the wild:
  `label` (identifier, e.g. `human`/`persona`), `value` (the actual text — the reasoning content),
  `description` (guides how the block should be used), `limit` (char cap, default 2000), `read_only`
  (dev-only vs agent-editable). Blocks are **compiled into the system prompt on every step**. Tiered:
  **core** (in-context, RAM), **recall** (searchable history, disk), **archival** (tool-queried, cold)
  ([Letta docs: Memory blocks](https://docs.letta.com/guides/agents/memory-blocks/);
  [Letta blog: Memory Blocks](https://www.letta.com/blog/memory-blocks/);
  [DeepWiki: Letta agent memory system](https://deepwiki.com/letta-ai/letta/2.3-agent-memory-system)).
  → Note `description` + `read_only`: metadata that tells the model *when/how* to use the block, and a
  flag protecting authoritative facts from drift. Both belong in our node.

- **Zep / Graphiti — bi-temporal, provenance-preserving facts (most relevant to staleness/conflict):**
  entities = nodes, relationships = edges; **every edge carries temporal metadata**. **Bi-temporal**:
  it tracks *valid time* (when the fact was true in the world) AND *ingestion/transaction time* (when
  the system learned it) — `valid_at` / `invalid_at` (plus learned-at / learned-invalid-at). On a
  change it **does not overwrite**: it closes the old edge's validity window and opens a new one, so
  conflicting facts are **invalidated, not discarded**, preserving a queryable history + provenance
  ([Neo4j: Graphiti knowledge-graph memory](https://neo4j.com/blog/developer/graphiti-knowledge-graph-memory/);
  [Zep: What is a temporal knowledge graph](https://www.getzep.com/ai-agents/temporal-knowledge-graph/);
  [Zep AI review 2026](https://baeseokjae.github.io/posts/zep-ai-agent-memory-review-2026/)).
  → This is the exact mechanism we want for our `knowable_asof` no-look-ahead gate (RESEARCH C §5) and
  for 07.6 bitemporal cutoff. Two timestamps per fact: *when it was knowable* and *when we recorded it*.

- **Mem0**: memories as vector embeddings via an extract→consolidate→retrieve loop (v3 = single-pass
  ADD-only extraction with cross-memory entity linking). A bolt-on memory *layer* rather than a schema
  ([Mem0 vs Letta](https://vectorize.io/articles/mem0-vs-letta);
  [Mem0 vs Letta vs Zep](https://plur.ai/blog/mem0-vs-letta-vs-zep/)).

### 2.7 Agentic-RAG node authoring guide — field checklist

A practical RAG-KB guide crystallizes the node contract for retrieval agents:

- **Single-topic chunking**: "each focused on a single topic or question," "a few paragraphs (or even a
  few sentences) per chunk."
- **Applicability metadata** for filtering: "context about when or to whom a chunk applies" — e.g.
  "Return Policy (California customers)", "Procedure: Password Reset (Android)."
- **Directive body**: "write like you're instructing a particularly literal intern — clear and direct…
  imperative language"; strip marketing fluff.
- **Explicit outcome statement** in the chunk: e.g. "Outcome: Appointment is canceled and a
  confirmation email is sent."
- **Continuous curation vs staleness**: "not set and forget" — trace weird answers back to the source
  chunk and remove outdated info promptly
  ([Regal.ai: The RAG Playbook — structuring knowledge bases](https://www.regal.ai/blog/rag-playbook-structuring-knowledge-bases)).

## 3. Synthesis — the structured-vs-narrative split (what to copy)

Merging §1–§2, here is the division of labor every system uses, expressed as a spec.

### 3.1 STRUCTURED fields (deterministic; power routing / retrieval / filtering / safety)
The model never "reasons" from these — the *retrieval and gating layer* does. They answer *does this
node apply, and can I trust/see it right now?*

| Field | Purpose | Seen in |
|---|---|---|
| **type / kind** | route to the right playbook family | DoorDash FSM states, kb.py `kind`, Letta `label` |
| **applicability / scope tags** | filter to matching situation (region, product, here: indication/modality/catalyst-type) | Regal, Sierra, kb.py filters |
| **validity window** (`valid_at`/`invalid_at`) | temporal correctness; invalidate-don't-delete | Zep/Graphiti bi-temporal |
| **knowable-as-of** (transaction/ingestion time) | no-look-ahead at application | Zep ingestion time; RESEARCH C §5 |
| **confidence** | rank / gate low-trust nodes | DoorDash, kb.py `confidence` col |
| **outcome label (enum)** | deterministic, machine-readable result | resolved-case pattern; our outcome enum |
| **signed magnitude** (here: realized move) | quantitative, not prose | DoorDash structured memory |
| **source refs / citations** | grounding + provenance | CITES edges; Zep provenance |
| **read-only / authoritative flag** | protect facts from drift | Letta `read_only` |
| **version / release id** | reproducibility, regression | Sierra immutable snapshot |

### 3.2 NARRATIVE fields (rich natural language; the model reasons from these)
Answer *what happened, WHY, and what to watch/do* — the thing embedded and put in context.

- **Written at the right altitude**: heuristics + concrete signals, not brittle rules, not vague
  (Anthropic). Directive, literal, fluff-free (Regal).
- **Single-topic, a few paragraphs.** One catalyst / one scenario per node.
- **States an explicit outcome/resolution** in the body (Regal), and — for us — the causal drivers and
  the pre-catalyst tells.
- **Grounded**: each claim traceable to a `source ref`; deterministic facts (the move, the label) come
  from structured fields/systems, not from the prose (DoorDash "doesn't rely on the LLM alone").

### 3.3 Keeping it grounded, and avoiding stale/conflicting entries
- **Cite-or-drop** every driver/outcome (already our `insert_claim` invariant; matches DoorDash
  groundedness guardrail + Zep provenance).
- **Invalidate, don't overwrite**: on a superseding fact, close the old validity window and open a new
  node/edge (Zep). Preserves history, kills the stale-vs-new conflict without losing the audit trail.
- **Snapshot the knowledge with the decision** (Sierra) so a past recommendation can be replayed
  against exactly the playbook that produced it.
- **Curate via the eval loop**: trace bad reasoning to the source node (Regal); run the DoorDash-style
  LLM-Judge (retrieval correctness / faithfulness / relevance) + guardrail (groundedness) over the
  playbook, and turn confirmed-bad cases into regression tests (Sierra).

## 4. RECOMMENDED node structure for OUR catalyst-outcome playbook node

Two node types, both stored via the existing `kb.py` scaffold (RESEARCH C): a **per-catalyst analog
node** (one real past event) and a **per-scenario playbook node** (the generalization). Everything
below goes in `KBNode.attrs_json` unless it's already a first-class column (`kind`, `confidence`,
`ref_id`) or an edge (`RESULTED_IN`, `CITES`) or the vector (`kb_vec`).

### 4.A Per-catalyst analog node — `kind="catalyst"` (+ `RESULTED_IN` → `kind="outcome"`)

**STRUCTURED (filter/route/gate — read by `analog_query`, never "reasoned" from):**
```jsonc
{
  // --- routing / filtering ---
  "catalyst_type": "PDUFA | trial_readout | AdCom | earnings",   // -> analog_query filter
  "ticker": "XXXX",
  "indication": "NSCLC",            // scope tags (Regal applicability); enable type+indication filter
  "modality": "mAb | small_molecule | gene_therapy | ...",
  "phase": "Ph3 | PDUFA | ...",
  // --- temporal correctness (Zep bi-temporal; RESEARCH C §5) ---
  "knowable_asof": "2024-03-01",    // valid/ingest boundary -> the no-look-ahead gate at APPLICATION
  "event_date": "2024-03-15",
  // --- authoritative, deterministic facts (NOT prose) ---
  "confidence": 0.9,                // also the kb_node.confidence column
  "read_only": true                 // authoritative attribution -> protect from agent drift (Letta)
}
```
Plus `ref_id` → the Phase-1 `catalyst.id` (don't copy data in), `CITES` edges → `evidence_source`
nodes (mandatory grounding), and one `kb_vec` row embedding the **retrieval-context string** (§4.C).

**Linked `kind="outcome"` node (`RESULTED_IN` edge), STRUCTURED:**
```jsonc
{
  "label": "approve | CRL | hit | miss | mixed | beat | miss",   // outcome enum
  "signed_move": -0.42,             // realized signed move (quantitative, not prose)
  "confidence": 0.8,
  "asof_window": "T-1..T+1"
}
```

**NARRATIVE (the body the model reasons from — a few paragraphs, right-altitude, cited):**
Store as a single `narrative` attr (or a few labeled sub-fields, mirroring Letta's `value` +
Anthropic's section labels). Recommended sub-sections:
- `what_happened`: 2–4 sentences — the event and its result, stating the outcome explicitly (Regal).
- `why` (drivers): the causal factors that drove the outcome — endpoint design, prior effect size,
  mechanism precedent, FDA/AdCom/CRL history, safety signal, financing/runway, competitive/label
  position — **each with an inline source ref**.
- `what_to_watch` (pre-catalyst tells): the signals that *were knowable before* the event and pointed
  at the outcome — the transferable heuristic for a future analog.
- `caveats`: base-rate/sample warnings; why this analog may not transfer.

### 4.B Per-scenario playbook node — `kind="playbook"` (via `insert_playbook`)

Same envelope, but the narrative is the **generalization** across many catalysts of a
`scenario_type` (e.g. "Ph3 primary-endpoint readout in immuno-oncology"): the recurring drivers, the
base rate, the typical move distribution, and the standing "what-to-watch" checklist — an AOP-style
heuristic body (Decagon) grounded to the member catalysts via `CITES`/`ANALOG_OF`, with a `version`
attr so it can be snapshotted with the decision that used it (Sierra).

### 4.C What gets embedded (`kb_vec`) — retrieval-context string
Keep RESEARCH C's contract (`"{ctype} catalyst for {target}: {verdict.thesis}"`) but **embed the
narrative body, not the structured fields** — structured fields are for the SQL pre-filter, the
narrative is what carries semantic meaning. This is the universal split: filter structurally, then
rank by narrative similarity (DoorDash condense→match, Fin retrieve→rerank).

### 4.D Grounding, staleness, versioning (apply §3.3 to our KB)
- **Cite-or-drop**: enforced by `insert_claim` (`CITES` mandatory) — matches DoorDash groundedness.
- **No overwrite on conflict**: if a later filing revises an attribution, write a new node and set the
  old node's validity closed (`invalid_at`) rather than editing in place (Zep). Retrieval prefers the
  node valid as-of the decision date.
- **No-look-ahead at APPLICATION only**: `analog_query` gates on `knowable_asof` (RESEARCH C §5); the
  hindsight-rich `why`/`what_to_watch` narrative is fine to *construct* with hindsight, but retrieval
  must only surface what was knowable then.
- **Snapshot**: stamp each playbook node with a `version`; record which playbook version fed a given
  recommendation so it's replayable (Sierra immutable snapshot).
- **Eval loop**: score retrieved-analog quality with a DoorDash-style LLM-Judge (retrieval correctness,
  faithfulness, relevance) + a groundedness guardrail; promote confirmed-bad retrievals into regression
  fixtures (Sierra). This is the curation mechanism that keeps the playbook from rotting.

### 4.E One-line rationale for each borrowed choice
- Structured envelope / narrative core → DoorDash, Sierra, Decagon, Letta all split this way.
- `read_only`/authoritative flag + `description`-style usage hint → Letta memory-block schema.
- `valid_at`/`invalid_at` + `knowable_asof`, invalidate-don't-delete → Zep/Graphiti bi-temporal.
- Right-altitude, sectioned, cited narrative → Anthropic context engineering + Regal RAG guide.
- Version snapshot + regression-from-annotations → Sierra ADLC.
- Deterministic facts (move, label) out of the prose → DoorDash "doesn't rely on the LLM alone".
