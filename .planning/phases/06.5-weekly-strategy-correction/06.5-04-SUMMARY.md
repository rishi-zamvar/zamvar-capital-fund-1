# Phase 06.5 Plan 04: Weekly Runner + run_portfolio Threading + WEEK-05 Record Seam Summary

The final plan of the weekly-strategy correction: a thin `desk/weekly.py::run_weekly` that composes the
shipped desk end-to-end into a weekly cadence (WEEK-01) — Fri-close `thesis_scan` on ALL names →
shortlist (catalyst names + top-k eligible statistical rows) → `run_desk` on catalyst names →
single-leg statistical Candidates ∪ catalyst legs → `run_portfolio` (now threading the ~1% target
within the survival cap, the statistical-sleeve cap, and the defensive-book fallback) → a
StrategyDossier book that is NEVER empty — plus the WEEK-05 per-leg outcome record seam that persists
realized weekly outcomes as cited KB claims for the Phase-10 LEARN loop. No new money logic: every
number comes from the shipped tools.

## What Was Built

- **Task 1 — `run_portfolio` threading (orchestrator.py + portfolio.py):** four keyword-only opt-ins —
  `target_return`, `defensive_book`, `extra_candidates`, `statistical_sleeve_cap`. With `target_return`
  set, `risk.assess` is called with `target_return=` and `expected_move=proposal.expected_return_pct`
  (net EV — the deliberate plan deviation from research's up_move); with it `None` the kwargs are OMITTED
  entirely, so the catalyst path is byte-for-byte Phase-5 (and the monkeypatched-assess stubs in
  `test_desk_portfolio.py` still bind). Statistical `extra_candidates` are merged into the ONE
  `select_book` pass; in a catalyst week `_cap_sleeve` caps the combined statistical book-weight at
  `statistical_sleeve_cap * weekly_budget` (dropping lowest-efficiency legs first) so the catalyst engine
  is never crowded out, while a pure-statistical week is left uncapped (the cap can never starve a
  no-catalyst week). `defensive_book` is threaded into `select_book`. Promoted single-leg
  statistical/defensive legs (payload without a `proposal`) are surfaced via the new deterministic,
  no-LLM `portfolio.build_weekly_leg_dossier` (hedge None, `which_risk_covered="none"`,
  `holds_through_catalyst=False`).
- **Task 2 — `run_weekly` + `build_defensive_book` (weekly.py, WEEK-01):** the thin composition. Reads
  the ONE `params['weekly']['anchor']` once and threads it into BOTH `thesis_scan` (measurement) and
  `_weekly_exit` (the one-week enter/exit horizon) — the measurement trap is closed. Shortlist = catalyst
  names + top-`shortlist_k` eligible statistical rows (ranked by `p * mean_next`). Statistical legs are
  SINGLE-LEG (no hedge — the Phase-5 fallback), sized `size_for_survival(p_loss=1-p,
  gap=abs(hard_veto_drop), target_return=target_weekly, expected_move=mean_next)`, always exiting at the
  one-week horizon. `build_defensive_book` builds SGOV/BIL/XBI cash anchors from params so a no-signal
  week deploys the defensive book instead of an empty one. The per-catalyst market context is a
  caller-injected `catalyst_context` hook (the price/analog feed is a documented carry-forward).
- **Task 3 — `record_weekly_outcome` (weekly.py, WEEK-05):** persists one KB `outcome` claim per realized
  leg — `{thesis_type, trigger, p_quoted, size, realized_ret, win}` — CITING the `weekly_base_rate`
  ToolResult via a `tool:weekly_base_rate#<inputs_hash>` ref stored as the claim's `EvidenceSource`, so
  `insert_claim`'s cite-or-drop invariant holds by construction. `run_weekly` calls it at the one-week
  exit for caller-supplied `closing_legs`. The refit that consumes these rows is Phase-10 (seam only).

## Deviations from Plan

### Design resolutions (within Rule 3 — the right factoring, not a corner cut)

**1. [Rule 3] Statistical/defensive legs wrapped as deterministic StrategyDossiers.**
- **Why:** the plan declared `run_weekly -> list[StrategyDossier]` but its defensive test described the
  return as "SGOV/BIL/XBI Candidates" — an internal tension. `run_portfolio` must keep returning
  `list[StrategyDossier]` (the Phase-5 suite cannot be modified), so promoted statistical/defensive legs
  are surfaced by `portfolio.build_weekly_leg_dossier` — a deterministic, NO-LLM builder (spending an opus
  PM call on an SGOV cash anchor would be waste + semantically wrong). These legs are marked
  (`catalyst_id="weekly:<kind>:<ticker>"`, hedge None, `which_risk_covered="none"`).
- **Files:** `src/catalyst_trader/desk/portfolio.py`, `src/catalyst_trader/desk/orchestrator.py`
- **Commit:** 765e704

**2. [Rule 3] `catalyst_context` injection hook for the per-catalyst market context.**
- **Why:** `run_desk`→`run_portfolio` needs `entry` + `risk_inputs` (p_loss/gap/analog_gaps/prices) per
  catalyst leg, but the desk has no live price/analog feed this phase (a documented PROJECT.md
  carry-forward). Per `run_portfolio`'s own contract ("the caller supplies it"), `run_weekly` takes a
  `catalyst_context` hook; `None` skips catalyst legs (statistical + defensive carry the book).
- **Files:** `src/catalyst_trader/desk/weekly.py`
- **Commit:** 6c74134

**3. [Rule 3] `assess` kwargs passed conditionally (only when `target_return` is set).**
- **Why:** literally byte-for-byte back-compat — the monkeypatched `assess` stubs in the untouched
  Phase-5 suite don't accept `target_return`/`expected_move`. Omitting the kwargs when `target_return is
  None` preserves the exact Phase-5 call.
- **Files:** `src/catalyst_trader/desk/orchestrator.py`
- **Commit:** 765e704

**4. [Rule 3] Statistical-leg survival gap = `abs(params['weekly']['hard_veto_drop'])`.**
- **Why:** `size_for_survival` needs a down-gap for statistical legs; the honest, param-sourced value is
  the worst tolerated weekly move (the falling-knife threshold). Reuses an existing param — no new key,
  no literal in the runner.
- **Files:** `src/catalyst_trader/desk/weekly.py`
- **Commit:** 6c74134

Preserved verbatim per the plan: `expected_move = proposal.expected_return_pct` (net EV, NOT up_move) for
catalyst legs; statistical legs single-leg via the Phase-5 no-hedge fallback; one anchor everywhere.

## Known Stubs

None that block the plan's goal. Two honest, documented seams (upgrade paths, not stubs):
(1) the `catalyst_context` hook is `None` by default — the live price/analog feed is a PROJECT.md
carry-forward (free-data fetcher / web-scraper data layer); statistical + defensive sleeves fully carry
the book offline meanwhile. (2) `record_weekly_outcome` is the WEEK-05 SEAM — it persists raw cited
outcomes; the base-rate refit + eligibility/auto-demotion ledger that CONSUME them are Phase-10 (LEARN),
explicitly out of scope (marked `# ponytail:`).
