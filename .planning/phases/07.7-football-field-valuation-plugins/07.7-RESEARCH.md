## Summary

A "football field" is the standard sell-side/PE horizontal-bar chart that stacks the value (or, here, the **expected move**) implied by every independent method side-by-side on one common axis, so the reader sees the range, the overlaps, and the **convergence zone** where methods cluster. The convergence zone — not the arithmetic mean — is what anchors the recommendation ([IB Offer](https://iboffer.com/blog/football-field-presenting-valuation-range), [IBIQ](https://ibinterviewquestions.com/guides/valuation-investment-banking/football-field-synthesizing-multiple-methods)).

Our target is not a fair-value price; it is the **expected one-week absolute % move magnitude** around a binary catalyst (PDUFA / Ph3 readout / AdCom). Most classic football-field bars (trading comps, precedent transactions, LBO, 52-week range) **do not translate** to a one-week event move for a pre-revenue biotech and should NOT be built. The methods that DO translate are already almost entirely present in `quant/`: analog-gap mixture (`catalyst_move_estimate`), options-implied straddle (`implied_move`), statistical base-rate move (`weekly_base_rate`), and PoS-weighted approve/CRL scenario (built by feeding **rNPV-derived** approve/CRL scenario moves back through `catalyst_move_estimate`). The **only** genuinely missing pieces are (1) the aggregator itself and (2) a small analyst-price-target dispersion function.

**Primary recommendation:** Build exactly **two** new canonical plugins — `quant/field.py::expected_move_field` (the aggregator; convergence = **confidence-weighted trimmed median** of per-method magnitudes + a dispersion/agreement score) and `quant/valuation.py::analyst_pt_move` (price-target implied-move dispersion). Everything else is PARAMETERIZE-existing. Wire the field magnitude into `builder.py::build` (repurpose the existing `TradeProposal.expected_return_pct` display field), add a deterministic `dd_expected_move` seam + `DiligenceDossier.dd_expected_move` field, and add ONE comparator line to `md.py::cross_check`. The reconcile loop-back already exists.

## 3. The Assembly + Convergence Rule (the heart)

### Options evaluated

| Rule | Pro | Con for our case |
|------|-----|------------------|
| Naive mean | trivial | sensitive to a single junk method (illiquid IV, cold-start analog) — the user explicitly rejects it |
| **Median** | outlier-robust, no weights | ignores that methods differ in reliability |
| **Trimmed mean** | robust, interpolates mean↔median | little consensus it beats median; needs a trim fraction |
| **Confidence/inverse-variance weighting** | theoretically optimal if per-method error variances are known | we have **no reliable per-method error variances** (5–7 methods, few obs, cross-correlated) → estimated weights are noisy; the "forecast-combination puzzle" is that estimated-weight schemes routinely **lose** to simple robust combiners ([Wang & Hyndman review](https://arxiv.org/pdf/2205.04216), [Stock & Watson](https://www.princeton.edu/~mwatson/papers/apf_3.pdf)) |
| **Bayesian model averaging** | principled | overkill; needs priors/likelihoods we don't have at this scale |
| **Cluster/mode detection** ("pick where methods cluster") | matches the user's phrasing literally | needs an arbitrary bandwidth; unstable with 5–7 points |

### RECOMMENDATION: confidence-weighted **trimmed median** + explicit dispersion

The point estimate = the **weighted median** of the per-method magnitudes (after dropping abstaining methods), with an optional symmetric trim of the most extreme contributions. Rationale:

1. **It is the computable, stable proxy for the "convergence zone."** The weighted median sits in the densest, most-agreed region and is immune to one outlier method — exactly "the value the most signals point to," without an arbitrary kernel bandwidth. This is the lazy-correct version of cluster detection.
2. **Robust > optimal when weights are noisy.** The literature is clear that with few, correlated forecasts and no clean error history, simple robust combiners (median, trimmed mean) match or beat inverse-variance/Bayesian schemes ([trimmed-mean robustness](https://rdrr.io/cran/GeomComb/man/comb_TA.html), [Wang & Hyndman](https://arxiv.org/pdf/2205.04216)). Building inverse-variance weighting here would be complexity that underperforms.
3. **Confidence weights we DO have are structural, not fitted.** Each existing tool already emits a reliability signal in `detail`: `catalyst_move_estimate` → `cold_start` / `n_up`+`n_down` / `source`; `weekly_base_rate` → `n_effective` / `shrunk` / `ci_low`; `implied_move` → liquidity (gated upstream). Map these to a small ordinal weight (e.g., cold-start/illiquid = low, ample-n = full). That's a defensible weight without inventing an error model.
4. **Abstention, not zero.** A method with no valid inputs (illiquid options, empty analog branch and no prior, missing PT list) contributes **nothing** — it is dropped from the median, never entered as 0 (which would bias the estimate toward zero). This mirrors the existing `_branch_magnitude` fallback discipline in `events.py`.

### Surfacing disagreement (feeds the DD-vs-builder check)

Compute a **dispersion** measure across the surviving method magnitudes — recommend the **coefficient of variation** (std/mean) or the IQR/median ratio — and classify agreement (`"tight"` vs `"wide"`) against a params threshold. This dispersion is:
- returned in the aggregator's `detail` for the memo/UI (the range + where bars cluster), and
- the natural signal that the **builder's** convergence number and **DD's** independently-derived `dd_expected_move` should be checked against each other in `cross_check` (§5). Wide dispersion OR a large builder-vs-DD gap → a `RetriggerFlag` the reconcile loop already routes.

### 4.1 MISSING #1 — `analyst_pt_move` (small, generic)

Home: **`quant/valuation.py`** (a valuation-consensus method). Generic math only; PT list injected at call time.

```python
def analyst_pt_move(current_price: float, price_targets: list[float]) -> ToolResult:
    """Street price-target implied one-week-agnostic move magnitude + dispersion.

    value = median(|pt - current_price| / current_price) over the PT list — the robust
    central street-implied move magnitude. detail carries high/low implied moves, the raw
    dispersion (IQR/median), and n. Raises on current_price<=0, empty list, or any
    non-finite target (Pattern 2 — never a misleading NaN). No company constant baked in.
    """
```
Returns `ToolResult(tool="analyst_pt_move", tool_version="1.0.0", inputs={...verbatim...}, value=<median move magnitude>, detail={"high": ..., "low": ..., "dispersion": ..., "n": ...})`.

### 4.2 MISSING #2 — `expected_move_field` (net-new core aggregator)

Home: **`quant/field.py`** (its own module, per CONTEXT rule #4 — it aggregates across valuation+options+events+weekly and belongs to none of them).

**Design choice (ponytail):** the aggregator consumes a list of **already-normalized method contributions** — `{"method": str, "magnitude": float, "weight": float, "ref": str}` — that the **caller** extracts from each heterogeneous ToolResult (they store the magnitude in different fields: `catalyst_move_estimate.detail`, `weekly_base_rate.detail.mean_next`, `implied_move.value`, `analyst_pt_move.value`). This keeps the aggregator generic and the per-tool extraction explicit and testable, instead of coupling the aggregator to every tool's quirks. Abstaining methods are simply omitted from the list.

```python
def expected_move_field(methods: list[dict], params: dict) -> ToolResult:
    """Assemble the expected-move football field → the convergence point estimate.

    methods: [{"method": str, "magnitude": float (>=0), "weight": float (>0), "ref": str}]
             — abstaining methods are omitted by the caller, never passed as 0.
    params["field"]: {"min_methods": int, "trim_frac": float, "dispersion_wide": float}
             — every threshold read by direct subscript; a missing key RAISES (no literal).

    value  = confidence-weighted trimmed MEDIAN of the surviving magnitudes (the convergence
             zone — outlier-robust, sits where the most-weighted methods cluster).
    detail = {contributions, point_estimate, low, high, dispersion, agreement ("tight"/"wide"),
              n_methods, method_labels, refs}. Raises if n_methods < min_methods (no false
              precision from a one-method 'field').
    """
```
Returns the standard frozen `ToolResult`. `value` is the **magnitude**; the caller applies the debate sign.

## 7. New-Analysis-as-Plugin Convention

The canonical, stored-plugin pattern (already the de-facto convention across `quant/`):

1. **Pure function in the correct module** returning a frozen `ToolResult` (`result.py`: `tool`, `tool_version`, verbatim `inputs`, `value`, `detail`). Bump `tool_version` when the formula changes.
2. **Validate at the boundary, RAISE on out-of-domain** (Pattern 2 — never emit a misleading NaN/inf). Reuse `_finite`/`_prob` helpers.
3. **All thresholds from a `params` dict; a missing key raises** — no numeric literal in the tool body. Company constants come from the playbook (§6), injected as arguments.
4. **TDD:** a `tests/test_<module>.py` shipped *before* the logic, BDD-named, exhaustive edge cases (empty inputs, single method, abstentions, wide-dispersion, all-agree, non-finite guards). Hand-computed happy path like `test_rnpv_happy_path_hand_computed`.
5. **Register for reuse:** add to `quant/__init__.py` imports + `__all__`.
6. **Expose to agents (if an agent calls it):** add an `@tool` wrapper in `desk/tools.py::build_quant_tools` and to `diligence.ALLOWED_TOOLS`. That is the "stored plugin, callable by any future agent" step — a plugin is not "registered" until it is in the MCP surface.

For this phase: `expected_move_field` and `analyst_pt_move` follow all six steps. `expected_move_field` is primarily called by desk Python (builder/DD), so the MCP wrapper is optional this phase — add it if an analyst dimension needs to call it directly; otherwise defer (YAGNI).

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Approve/CRL scenario move | a new `scenario_move()` | `catalyst_move_estimate` with single-element branches | duplicate of the locked mixture — the exact confusion the no-dup rule prevents |
| Statistical move | a new next-week move calc | `weekly_base_rate(...).detail["mean_next"]` | already computed, anchored, shrunk |
| Options move | a new IV/straddle calc | `implied_move` | exists; straddle already preferred |
| rNPV | any per-company valuation fn | `rnpv` + per-company playbook args | exists; company values are playbook data |
| Optimal combination weights | inverse-variance / Bayesian weighting | confidence-weighted trimmed median | no reliable error variances; robust beats estimated-weights here (forecast-combination puzzle) |
| The reconcile loop-back | any new re-trigger routing | `md.reconcile` cascade + `_workitem` | fully wired in Phase 6.7 |
| Per-company assumptions storage | a new table/module | `insert_playbook`/`query_playbooks` scenario_type `assumptions:<ticker>` | playbook table + citation invariant already exist |

## Common Pitfalls

1. **Entering an abstaining method as 0.** Biases the convergence value toward zero. Drop it from the list; enforce `min_methods` so a one-method "field" raises instead of pretending precision.
2. **Voting on sign.** The field combines **magnitudes**; the sign is the debate verdict's alone (locked `catalyst_move_estimate` rule). Combining signed values would let a bullish method cancel a bearish magnitude — meaningless for an expected-move.
3. **Mixing axes.** rNPV is a *value*; it must be converted to a % move `(rnpv−price)/price` before it joins the move field. Never put a dollar value and a % move on the same axis.
4. **Building the non-translating classic methods** (comps/precedent/LBO/52-wk). They produce no one-week catalyst move for pre-revenue biotech; they'd inject noise bars. Explicitly out of scope.
5. **Destabilizing the survival sizing path.** The field number is display/reconciliation; keep `size_for_survival` on `catalyst_move_estimate.down_move` this phase.
6. **Putting `field` thresholds in `DILIGENCE_PARAMS`.** DD gate thresholds are deliberately decoupled from the strategy param seam; `field` knobs belong in `load_params`.
7. **A literal in the aggregator body.** `trim_frac`/`min_methods`/`dispersion_wide` must come from `params["field"]` (missing-key-raises), like every other tool.

## Open Questions

1. **Confidence-weight scale.** How to map each tool's structural reliability flags (`cold_start`, `shrunk`, `n_effective`, options-liquidity) to a numeric weight.
   - Known: each tool exposes these in `detail`.
   - Unclear: exact ordinal levels.
   - Recommendation: a small `params["field"]["weights"]` table (e.g., `{"analog_cold": 0.5, "analog_warm": 1.0, "implied_liquid": 1.0, "base_rate_thin": 0.5, ...}`) read from the playbook — keeps weights out of the tool body and refit-able in Phase 9.
2. **`move_discrepancy_tol` starting value.** No calibration yet; seed conservatively (e.g., 0.35 = 35% relative gap) in the bootstrap CSV, labeled uncalibrated, refit in Phase 9. LOW confidence on the number, HIGH on the mechanism.
3. **Trim vs pure median.** With 3–5 surviving methods, trimming may drop too many. Recommend `trim_frac=0.0` default (pure weighted median) and only trim when `n_methods` is large. Ships as a param, so it's tunable without code change.
