Why we de-duplicate the playbook

Twelve extraction agents built the warm playbook in parallel. A few of them, racing on the same catalyst, wrote it into the knowledge base twice. Here is why a duplicate is not harmless — and how we remove it without losing a single fact.

01What actually happened

The warm playbook is one node per historical catalyst — an FDA decision or a trial readout — carrying the numbers and the story of what happened and why. We populated ~268 of them at once by running agents side-by-side, each taking a chunk.

The write path is idempotent by content: re-inserting the identical record for a catalyst is a no-op. But two agents that read the same catalyst and phrase its narrative even slightly differently produce two records with two different content-hashes — so the database keeps both. That is the only way a duplicate is born here: not a bug in the data, but two writers arriving at one event at the same moment.

The important part A duplicate is not a corrupted row. It is a second, valid copy of a real event. Which is exactly what makes it dangerous — it looks legitimate to every part of the system that reads it.

02Why a duplicate quietly distorts the desk

When the Trade Builder faces a new catalyst, it does not use one model. It asks the playbook: "show me the most similar past events, and what happened to them." It pulls the handful of nearest analogs and lets them vote on the expected move — the "football field." That vote is only fair if each past event counts once.

A duplicated event votes twice. It steals a neighbor slot that a genuinely different precedent should have held — so the estimate bends toward one story and reports false confidence in it.

1

Analog vote-stuffing

The nearest-neighbor search does not de-duplicate. A repeated event occupies extra slots in the top-k and over-weights its own outcome in the expected-move estimate.

2

False precision

Two identical outcomes shrink the apparent spread. The desk sees agreement that is really one event echoing itself, and sizes the trade as if it were surer than the evidence warrants.

3

Cohort-count inflation

The system narrows to an indication-specific cohort only when it has "enough" precedents. Duplicates inflate that count, flipping the switch on thin evidence.

4

Lesson over-weighting

When recurring lessons graduate into standing playbook rules, a duplicated event's lesson is counted twice — a single anecdote masquerading as a repeated pattern.

03How we remove one without losing anything

Because a duplicate is a valid copy, deleting one is money-adjacent surgery — done carefully and reversibly. Three gates stand before anything is destroyed:

1 · Store

Every node we might drop is first written out in full — its narrative, drivers, citations, outcome, and links — to a recoverable archive. Nothing is deleted before it is saved.

2 · Audit

A separate agent reads the keeper against the drop and confirms the keeper holds every fact, driver, and citation in the copy. If the copy has anything unique, it's flagged, not deleted.

3 · Apply

Only then, in one transaction: remove the copy, its outcome, its links, and any citation left orphaned — verifying zero broken links and zero remaining duplicates before committing.

Which copy we keep We keep the newest version of each catalyst — the same "newest wins" rule the pipeline already uses everywhere else. For the handful of FDA-decision records that were deliberately re-written to correct a label, the newest copy is the correction. The audit exists to catch the case where the newer copy is not, in fact, the better one — the confidence number alone can mislead, so we read the whole story.

One thing worth your eye Several FDA-decision records carry a known tension: a rule labels the outcome purely by the stock's move, so a few real approvals that sold off got stamped as rejections. The agents flagged each one in its narrative rather than hiding it. That's a separate refinement (a size-aware label rule) — noted here so it isn't mistaken for a duplication issue.
