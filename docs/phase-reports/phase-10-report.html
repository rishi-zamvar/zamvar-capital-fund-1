Phase 10 — Continuous-Iteration Loop

● BUILT + VERIFIED · LEARN-01 + LEARN-02 · 2133 tests · judge awaiting your labels
2026-11-11 · branch phase10-learning-loop · goal: the desk gets measurably better every week — but can never quietly overfit or reward-hack the money path.

✓ What's done

  • A judge grades every resolved paper trade (LEARN-01). After a trade closes and Phase 8 attributes it, an LLM judge scores the desk's call 1–5 against what actually happened (right direction for the right reason, or luck from the sector tape). The judge runs with no tools at all.
  • The judge has to earn trust. A calibration harness compares it with hand-graded labels: agreement (kappa ≥ 0.6, within one grade ≥ 80%) on at least 20 real labels. Until it passes, every score is stored as uncalibrated, and the database refuses any row that claims otherwise.
  • The loop proposes config changes but cannot apply them by itself (LEARN-02). Proposals can only touch a short whitelist of weekly knobs, inside bounds. The safety knobs (the −15% falling-knife veto, binary-catalyst gaps, the defensive book) cannot be tuned, and the tradeability bar can only be tightened.
  • Every change has to pass a gate. The gate replays a golden set of stress windows (the change must not do worse on any of them), checks guardrails (drawdown floor), and runs a walk-forward test on a frozen holdout: it must win most folds, beat XBI-relative alpha, and clear a deflated Sharpe that gets stricter with every test run against the same holdout.
  • No look-ahead. Proposals are trained only on data that ends one embargo week plus one hold week before the holdout. Any attempt to read further raises an error.
  • The rule is built into the database, not just the code. Migration 020 refuses any new weekly-config version, or any config version above the seed tier, unless it carries a one-time ticket from a passed gate run with the exact same values. Versions can't be edited in place. 39 adversarial tests try to get around it: forged fields, changing a diff after it passed, tampering with the holdout, writing to the KB directly or rewriting a node into it, forging a verdict or flipping a status, replaying a ticket, and dropping the trigger. All of them are refused. One residual is documented: someone with raw SQL access can still fabricate a passed gate run.
  • Weekly commands: --freeze-holdout, --learn (judge, propose, gate; applies nothing) and --promote ID (you apply a change that passed).

! Needs your review / input

C1 · Grade 20+ real trades

All 10 labels in data/learn/judge_labels.json are synthetic placeholders I wrote to exercise the harness. The judge stays uncalibrated until you grade real resolved cases.

C2 · Golden-set windows

I seeded the 2020 COVID crash, the spring 2022 XBI capitulation and the summer 2022 rebound (needs_ceo_review). Confirm them or replace them with cases you care about.

C3 · Freeze the first holdout

Choose the evaluation window on the real database. Its end must be at least one week before the newest bar. The holdout allows 20 gate runs, then you re-freeze.

D1 · Auto-promote?

Default: a change that passes still waits for your explicit --promote. Switching to auto-apply on pass is a one-line change you would need to authorise.

D3 · Floors

min DSR 0.90, kappa 0.6, within-one 0.8, 20 labels, 12 holdout weeks. All are documented defaults for you to retune.

★ What's going well

Reuse, not rebuild: the gate runs the Phase 7 Layer-A backtest, the Phase 8 attribution, the existing deflated Sharpe and XBI tools, and the single SDK seam. The new code is one small package (learn/) and two migrations.
Plan-check caught two real money-path holes before any code was written: a low-confidence weekly config could have slipped in unchecked, and the leak boundary ignored the exit fill.
