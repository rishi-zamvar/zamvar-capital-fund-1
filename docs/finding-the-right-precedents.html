Finding the right precedents

We gave the playbook a way to match a new event to similar past situations. When we tested it, it didn't help yet. Here's what that means, why, and exactly how we make it work — no jargon.

THE GIST

The playbook is meant to work like a seasoned analyst's memory. A new drug event comes up, and the system asks: "what past events were like this one, and what happened to them?" Everything depends on pulling up the right past events.

Think of it as a filing cabinet of 470 past cases. The whole trick is grabbing the folders that actually rhyme with the situation in front of you — not just any folder from the same drawer.

To help it match, we put little situation labels on every past case — sticky notes like "the good news was already expected" or "a tiny company betting on one drug." The plan: when a new event shows up, pull the past cases wearing the same sticky notes.

Result: no change yet

Across five test events, the matching was no better than before. The idea is right — but four fixable things are stopping it from working. None is fatal.

The four problems — and how we make each one strong

Each is explained the same way: what it means in plain terms, a real example from our own test, and the fix.

1

The new event barely gets any labels

the jargon term was: "query under-tagging"
What it means

Before an event happens, we only know a little about it. So when a new event walks in, we could only stick one label on it — and for earnings events, often zero. If the new event has only one sticky note (or none), there's almost nothing to match on, so the system falls back to "just grab anything from the same drawer."

Real example: Two of our five test events were earnings. Both got zero labels, so the smart matching never even switched on — it behaved exactly like the old system.
How we make it strongGet better at reading a new event's situation from what we do know ahead of time — its written thesis, its disease, its type of drug, whether the news was already public, how much cash the company has. Give every new event several accurate labels up front, especially earnings.
2

One label is stuck on half of everything

the jargon terms were: "over-broad tag" & "rarity-weighting / IDF"
What it means

One of our labels — "a tiny company betting on one drug" — ended up on roughly half of all 470 cases. Matching on a label that common is like sorting people by "owns a phone." It's true of almost everyone, so it tells you almost nothing.

Real example: For a muscle-disease drug (SRRK), all eight matches shared only that one super-common label — so the system handed back a grab-bag across totally unrelated diseases. Technically "matched," practically useless.
How we make it strongTwo moves. (a) Split the giant label into more specific ones (e.g. "tiny company, late-stage make-or-break trial" vs "tiny company, early hint of data"). (b) Make rare labels count more. A label on only 20 cases is far more telling than one on 235 — so a rare shared label should pull two cases together strongly, a common one barely at all. (That's all "rarity-weighting" means: the rarer the shared trait, the more it means.)
3

Sometimes we stuck the wrong label on

the jargon term was: "mis-tag"
What it means

Our labeler is a simple rule-of-thumb text scanner, so it occasionally mislabels a case. And because a new event only carries one or two labels, a single wrong label sends the whole lookup in the wrong direction.

Real example: A kidney-disease event (VERA) was wrongly labeled "a hard disease where drugs usually fail." That one wrong note steered the search straight into brain-disease cases (Alzheimer's, ALS) — zero kidney cases came back.
How we make it strongAdd a quality-check pass: sanity-check each label against the case's actual disease and drug, and flag suspicious ones before they ever reach a search. For the labeling itself, a smarter labeler (reading the full story rather than scanning for keywords) makes far fewer mistakes.
4

We forgot to match on the obvious thing first

the jargon terms were: "mechanism / indication axis" & "domain floor"
What it means

We matched only on the situation sticky notes and skipped the most obvious question a real analyst asks first: is this even the same disease, or the same kind of drug? A muscle-disease precedent and a psoriasis precedent can share a situation note, but they're not useful comparisons for each other.

Real example: For the muscle-disease drug, the system returned psoriasis and Alzheimer's cases that happened to share a situation label. Same "situation," wrong world.
How we make it strongGet the order right. First narrow to the same disease-area or type of drug (the "floor" — the non-negotiable baseline). Then use the situation labels to pick the best matches within that. Disease/drug is the foundation; situation is the refinement. We'd had it backwards — this is the single highest-impact fix.

Zooming in: what "better label quality" really means

Problems 2 and 3 are both really about label quality. A good labeling system needs three things:

Accurate

The label is actually true of the case. No kidney event tagged as a brain-disease graveyard. (Fixes problem 3.)

Specific

Labels carve the world into useful pieces — not one label smeared across half of everything. (Fixes problem 2.)

Weighted

Rare, telling labels count more than common ones, so a real match outranks a coincidental one.

The cheapest way to get all three: split the broad labels, weight rare ones higher, and upgrade the labeler from a keyword-scanner to one that reads the whole case (with a spot-check audit on top). None of this requires re-collecting any data — it's all refinement of what we already have.

Putting it together: the improved matching recipe

All four fixes combine into one better way of pulling precedents:

Start in the right world

Only consider past cases in the same disease-area or same type of drug. This is the floor — situation can never override it. (fix 4)

Give the new event a full, accurate read

From everything knowable beforehand, tag its real situation — several labels, not one, and right ones. (fixes 1 & 3)

Rank by meaningful overlap

Among the right-world cases, prefer those sharing the new event's situation labels — counting rare, telling labels much more than common ones. (fix 2)

Hand back the folders that truly rhyme

The analyst-agent now reasons from precedents that share both the world and the situation — the way a human PM actually thinks.

One thing that already works — keep it. We stopped letting the system lean on the company's ticker symbol to find matches, and it lost nothing: a company's own past events still surface on the strength of their story alone. That quietly removed a way the system could have fooled itself.

Why this is worth doing

When the memory pulls the right precedents, two things get better at once: the agent reasons about a new event from cases that genuinely rhyme with it, and the "expected move" estimate is built from realistic comparisons instead of noise. Get the matching right, and every downstream judgment the desk makes rests on a firmer floor.

Today the situation-label system is built and measured — a foundation, not yet a win. The test told us precisely which four things to sharpen. The biggest single lever is fix 4: match on the right disease and drug first, then let the situation refine it.
